# 把飞行判读写成 pytest 断言 —— 飞行的回归测试

> 这是 M2 的设计说明。面试问"你这个仓库最核心的东西是什么"，答案在这一页。

## 一句话

**把"这条飞行日志好不好"从人工看图，变成可重复执行、可机器判定、可进 CI 的自动化测试。**

## 为什么这件事值得做

传统无人机测试的判读方式是：飞完 → 打开 Flight Review → 看曲线 → 凭经验说"还行"。

问题有三个：

1. **不可重复**——同一个飞手，今天看和下周看，结论可能不一样；换个飞手看，标准又变了
2. **不可批量**——50 条日志要人工看 50 次，看第 40 条时注意力已经衰减
3. **不可回归**——改了 PID 参数重新飞，谁来判断这次比上次好还是差？只能靠印象

软件测试早就有答案：**把判据写成断言，让机器判断**。这套东西搬到飞行日志上，就是"飞行的回归测试"。

## 架构：测量与判定分离

```
                    ┌─────────────────────────────┐
   .ulg 日志 ──────▶│  pytools/flightdata.py      │
                    │  FlightData（只测量，不判定）│
                    │   · 定位稳定悬停段           │
                    │   · 算出 6 组指标            │
                    │  Thresholds（阈值集中定义）   │
                    └──────────┬──────────────────┘
                               │ 同一份测量
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
    ┌────────────────────────┐   ┌──────────────────────────┐
    │ pytools/ulog_report.py │   │ flytests/test_tc00*.py    │
    │ 生成人读的体检报告      │   │ pytest 断言，机器判定      │
    │ （给人看）              │   │ （给 CI 看）              │
    └────────────────────────┘   └──────────────────────────┘
```

关键点在中间那一层：**只有一份测量代码**。报告和用例消费同一份数据，永远不会出现"报告说 PASS、用例说 FAIL"这种自相矛盾。

很多人的做法是：脚本里写一套判读，测试里再写一套，两边慢慢走偏。这个仓库不这么干。

## 四个设计决策（每个都能讲）

### 1. 日志即测试数据

`conftest.py` 里 `data/*.ulg` 被自动发现成 pytest 参数：

```python
@pytest.fixture(scope="session", params=discover_logs(), ids=lambda p: Path(p).stem)
def flight(request) -> FlightData:
    return FlightData(request.param)
```

**新增一条飞行日志 = 新增一整组测试**，用例代码一行不改。这是测试数据与测试逻辑彻底解耦。

`scope="session"` 保证一条日志在整个测试会话里只解析一次（.ulg 解析是 IO + 解算密集操作，重复加载会拖慢）。

### 2. 先分段，再判读

这是最容易踩的坑。整条日志包含起飞爬升、悬停、降落三个阶段。如果对全程取 roll/pitch 极值，爬升时的俯仰前倾（可能 10° 以上）就会把一次完美的悬停判成 FAIL。

所以第一步永远是**定位稳定悬停段**：

```python
mask = (z < -0.8) & (abs(vz) < 0.3)   # 离地 >0.8m 且垂直速度 <0.3m/s
window = (ts[mask][0], ts[mask][-1])
```

只对窗口内的数据做统计。**这个"先选段再判读"的思路，本身就是测试设计的活教材**——不先界定"测的是什么场景"，后面所有数字都没有意义。

### 3. 断言消息即诊断报告

失败时不能只说"FAIL"，要说清楚：**实测多少、标准多少、往哪查**。

```python
assert m.roll_half_deg <= th.roll_deg, (
    f"{m.source}: 横滚 ±{m.roll_half_deg:.2f}°，超出标准 ±{th.roll_deg:.1f}°。"
    f"排查方向：横滚方向 PID 的 P 过大（等幅震荡）或 D 过小（回中慢）。"
)
```

对比一下：

| 差的写法 | 这个仓库的写法 |
|---|---|
| `assert roll < 1` | 报出实测 ±0.33°、标准 ±1.0°、以及 PID 的排查方向 |
| 挂了之后要重新翻日志找原因 | 挂的瞬间就知道该查什么 |

**测试报告的价值不在"通过/失败"，在"失败时能省多少排查时间"。**

### 4. 用例有效性要自己证明

一个全绿的测试集，可能是"真的没问题"，也可能是"断言根本没在工作"。

`make repro`（`scripts/negative_check.py`）对每一项判据**故意把阈值收紧到实测值之外**，看判定是否翻转：

```
[高度保持] 高度漂移收紧到 0.001 m
  实测：漂移 0.04 m（均高 2.50 m）/ 标准 0.0 m
  结果：✓ 断言有效（正确翻转为 FAIL）
```

翻转 = 断言真的在起作用；不翻转 = 断言写错了。这叫"测试的测试"，是 mutation testing 的手工简化版。

> 这个机制在开发时立刻抓到了一个真 bug：pyulog 返回的是 numpy 数组，比较结果是 `numpy.bool_` 而不是 Python `bool`，用 `is False` 判断会失效。已在 `FlightData.check()` 里统一 `bool()` 转换。

## 用例矩阵

| 编号 | 用例 | 判据 | 标记 |
|---|---|---|---|
| TC-001 | 悬停稳定性 | 悬停段 roll/pitch ≤ ±1°，高度漂移 ≤0.5m | `hover` |
| TC-002 | 动力裕度 | 悬停油门 45%~55%，峰值 <95%，波动 <15% | `hover` |
| TC-003 | 振动水平 | 三轴角速度峰值 <30°/s | `vibration` |
| TC-004 | 系统消息 | 全程零 ERROR（一票否决） | `safety` |
| TC-005 | 日志完整性 | 必备 topic 齐全、时长 ≥5s、采样率 ≥50Hz、时间戳单调 | `integrity` |

跑一次的结果（样例日志）：

```
14 passed, 1 skipped in 1.0s
```

## 怎么用

```bash
make test          # 全部用例
make test-hover    # 只跑悬停类
make test-safety   # 只跑一票否决项
make repro         # 验证用例本身有效
```

接 CI（GitHub Actions）时只需一句 `make test`，退出码非零即构建失败——README 顶部那个 badge 就是这么来的。

到那时，这个仓库就从"分析工具"变成"一条完整的飞行测试流水线"——一条命令从仿真到结论，中间不需要人。
